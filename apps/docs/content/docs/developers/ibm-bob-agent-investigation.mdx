このページは、IBM 社内向け AI コーディングアシスタント「Bob」を Multica の対応エージェントに追加する際の調査結果を記録した開発メモです。実装済みの内容ではなく、着手前に確認した事実と未確定事項をまとめたものです。関連 Issue: [MYP-367](https://github.com/nonmot/multica/issues) （GitHub Issue を参照）。

## IBM Bob とは

IBM 社内向けの AI コーディングアシスタント。IDE 拡張（Bob IDE、Roo Code/Cline のフォーク）と、ヘッドレスで動かせる CLI 版「**Bob-Shell**」（コマンドは `bob`）がある。中身は LiteLLM 経由で Claude 系モデルを呼び出しており、`AGENTS.md` を階層的にコンテキストファイルとして読む点は Multica 自身の規約と一致している。Multica のエージェント統合先としては CLI 版 Bob-Shell が対象になる。

> 訂正時の検証環境: `bobshell` v2.0.5（commit `2dc180906`、release 2026-09-22）。`bob --help` 系コマンドと同梱 `dist/bob.js` の実装からの静的確認が中心で、`BOB_API_KEY` 未設定のため実行自体は未検証（MYP-368 の設計調査時点、2026-09-26 訂正）。

Bob-Shell の非対話モードは次の形:

```
bob -p "<prompt>" --trust
```

`--trust` は実質必須。`security.folderTrust.enabled` が既定 `true` のため、未信頼ディレクトリでは `approval.autoApprovalEnabled` が強制的に `false` になり `createRunContext` が例外を投げる。`-m <model>` / `--approval-mode=auto_edit` / `--allowed-tools="..."` / `--checkpointing` / `--include-directories=...` / `--hide-intermediary-output` は存在しないフラグ（旧版メモの誤り）。`--yolo` は存在するが hidden/deprecated で、headless モードでは無視される（headless では auto-approve が既定のため）。

認証は `BOB_API_KEY`。`BOBSHELL_API_KEY` は非推奨のエイリアスで、設定すると値が `BOB_API_KEY` にコピーされるだけ。**両方を異なる値でセットすると hard error になる**（"Unset BOBSHELL_API_KEY and use BOB_API_KEY going forward."）。利用には w3publisher/bob での事前登録が必要。

## Multica 側の「新エージェント追加」の型

既存の 25 種類のエージェント（claude, codex, opencode, codearts, qwenpaw, zeroclaw, dim, mcode …）を見ると、追加は毎回ほぼ同じチェックリストをなぞっている（直近の追加例: `codearts` = migration 441、`zeroclaw` = migration 403 などから逆算）。変更点は次の一箇所に集約されている。

1. **バックエンド実装**: `server/pkg/agent/bob.go` を新規作成し、`Backend` インターフェース（`Execute(ctx, prompt, ExecOptions) (*Session, error)`）を実装。CLI の出力形式に応じて既存の実装パターンのどれかを踏襲する（後述の要確認事項参照）。`server/pkg/agent/launch.go`（起動コマンド引数のログ/redaction 許可リスト）と `server/pkg/agent/version.go`（`MinVersions` map）にも `bob` 用のエントリが必要。
2. **登録**: `server/pkg/agent/agent.go` の `SupportedTypes`、`launchHeaders` マップ、`New()` の switch に `"bob"` を追加。
3. **DB マイグレーション**: `server/migrations/NNN_runtime_profile_add_bob.{up,down}.sql` で `runtime_profile_protocol_family_check` の CHECK 制約に `'bob'` を追加（`NOT VALID` で追加するのが既存の作法）。
4. **デーモン側の配線**（`server/internal/daemon/`）:
   - `agents_probe.go` — `MULTICA_BOB_PATH` / PATH 上の `bob` バイナリ検出ロジックを追加
   - `config.go` — `Agents` map のコメント、エラーメッセージの一覧、`defaultAgentCommandNames` 相当のリストに `bob` を追加
   - `daemon.go` — 表示名マップ（例: `"bob": "IBM Bob"`）、SessionID scrape 系の例外リストなど、必要なら追加
   - `execenv/context.go`, `execenv/runtime_config.go` — コンテキストファイルはルートの `AGENTS.md` に加えて、モード別の `.bob/rules-{agent,ask,plan}/AGENTS.md` を読む（実機確認済み）
   - `local_skills.go` — スキル配置先は workspace `.bob/skills/<name>/SKILL.md` / global `~/.bob/skills/...`（優先順位は `.bob` > `.agents` > `.claude`、実機確認済み）
5. **メトリクス**: `server/internal/metrics/labels.go` の provider ラベル一覧に `bob` を追加。
6. **モデル一覧**（必要なら）: `server/pkg/agent/models.go`
7. **フロントエンド**:
   - `packages/core/types/agent.ts` の `RUNTIME_PROFILE_PROTOCOL_FAMILIES` に `"bob"` を追加
   - `packages/core/runtimes/display.ts` に表示名オーバーライド（デフォルト大文字化で足りなければ）
   - `packages/views/runtimes/components/provider-logo.tsx` にロゴ追加
   - MCP サーバー設定をパススルーするなら `packages/core/agents/mcp-support.ts` の `MCP_SUPPORTED_PROVIDERS` に追加
   - ランディングページの対応エージェント一覧（`apps/web/features/landing/i18n/*` の en/ja/ko/zh 各ファイル）にも `bob` の追加が必要
8. **ドキュメント**: `apps/docs/content/docs/providers.mdx`（およびその `.ja/.ko/.fr/.zh.mdx` 翻訳）の対応表、`install-agent-runtime.mdx`（+翻訳）にインストール手順を追加。
9. **テスト**: `server/pkg/agent/bob_test.go` を新規作成、`agent_supported_types_test.go` の一覧を更新、`scripts/agent-cli-command-names.txt` に `bob` を追加（デフォルトのテストは実在する CLI を実行しない規約があるため）。フロントエンドの対応エージェント一覧を検証している `*.test.ts` 2 本（`apps/web/features/landing/i18n/dictionary.test.ts` など）も更新が必要。

## 実装前に必ず確認すべき未確定事項

社内ドキュメント（Bob docs / Slack `bob-and-friends`）を調べた範囲では、下記が確認できなかった。これらは Multica のバックエンド実装方式（既存のどのパターンを踏襲すべきか）を決める前提になるので、実際に `bob` バイナリを用意して手元で検証する必要がある。

- **構造化出力の有無 → 解決（MYP-368 で確認）**: `bob --help` で確認した通り、`bob acp` サブコマンドが存在し、ACP (Agent Client Protocol) サーバとして起動できる。当初は「構造化 JSON 系」か「プレーンテキスト系」かの二択として提示していたが、実際には ACP という第三の選択肢があり、**MYP-368 ではこの `bob acp` 経路を採用**した（`dsh.go`/`grok.go` に近い ACP 系のバックエンド実装になる）。
- **セッション再開**: `--resume` 相当のフラグやセッション ID の出力があるか（`ExecOptions.ResumeSessionID` / `Result.SessionID` を実装できるかに直結）。ドキュメント上は確認できず。
- **モデル一覧の非対話取得 → 解決（MYP-368 で確認）**: `bob --list-models` 相当は無く、モデル選択自体が非対応（ACP の `session/set_model` を呼んでも "Model selection is not supported; use modes instead" と返る）。QwenPaw/MiniMax と同様、「Multica からモデル選択不可、ランタイム管理」扱いになる。
- **MCP 設定の渡し方**: `--mcp-config` 相当のフラグやファイルベースの設定があるか。
- **認証・利用登録**: Bob は IBMid ベースのサブスクリプション登録が必須（w3publisher/bob 経由、承認まで最短 1 日）で `BOB_API_KEY`（旧 `BOBSHELL_API_KEY`）をシークレットストアに保存する運用。Multica のデーモンをヘッドレスで動かすホスト（CI/サーバー）でこの登録・鍵配布をどう行うかは、コードの話ではなく社内の利用申請・ライセンス上の前提条件として別途確認が必要。
- **承認モードのマッピング → 解決（MYP-368 で確認）**: Bob 側の関連フラグは `--trust`（フォルダ信頼。未信頼だと `createRunContext` が例外を投げるため実質必須）と `--yolo`（hidden/deprecated、headless では無視され auto-approve が既定になる）の 2 つで、`--approval-mode` / `--allowed-tools` のようなフラグは存在しない。Multica 側のツール承認モデルとどう対応させるかは要検討。
- **ネストしたセッション**: Bob は子プロセスの環境に `BOB_SESSION=1` を設定し、既にこの変数がセットされていると起動を拒否する（`--allow-nested` で回避可能）。Multica デーモンからの起動時に環境変数の伝播を確認すること。
